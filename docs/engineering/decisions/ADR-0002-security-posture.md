## Context

Protocol Ward is a security-positioned product whose thesis is supply-chain awareness (`docs/product/pitch.md`). Pre-public, the project is solo-developed; a GitHub Actions workflow running on every push is theater without value. Locally enforced hooks and disciplined tooling deliver the actual security guarantees.

This ADR captures the policies that determine when and how code is validated against current CVEs, package-manager pinning, and the path from local enforcement to public-repo CI.

## Decision

### 1. No PR CI; workflows run only on release tags and a nightly schedule

`.github/workflows/` holds two workflows. `release.yml` runs only on `v*.*.*` tags (goreleaser + cosign). `nightly.yml` re-verifies `main` after merge (see the 2026-10-20 amendment below). Nothing runs on pushes or pull requests, and no workflow is a required check. All validation before merge happens locally via git hooks and `make ci`.

**Amendment (2026-10-05).** The original text deferred CI to sub-project 8 and expected a successor ADR to add CI as required checks when the repository went public. On 2026-10-05 the operator decided to go public as a beta **without** PR CI. Local hooks and `make ci` remain the gate for every change, and contributors run them (CONTRIBUTING.md). PR CI is reconsidered when outside contributions arrive (see Revisit conditions). No successor ADR is needed for the beta.

**Amendment (2026-10-20, issue #11).** Merged pull requests and web edits were never re-verified after merge, and `make dod`, the wasm smoke test and a goreleaser build ran only by hand or at tag time. `.github/workflows/nightly.yml` now runs against `main` on a daily cron and on `workflow_dispatch`. It detects breakage after merge; it is never a required check and never gates a merge, so the pre-push hook and `make ci` remain the gate. When `main` is unchanged since the workflow's last successful run, only `govulncheck` runs, because the vulnerability database is then the only input that changed. Otherwise it runs `make ci`, `make audit`, `make wasm-smoke`, `make dod` and a goreleaser snapshot build that neither publishes nor signs. The workflow sets `permissions: {}` at the top level and grants each job only what it uses (`actions: read` to find the last successful run, `contents: read` to check out, `issues: write` to report). Every action is pinned by full commit SHA, and no secrets are used. A failing run opens one issue labelled `ci:nightly-failure`; later failures comment on that issue, and the next green run closes it. GitHub disables scheduled workflows in a public repository after 60 days without repository activity, so the release checklist (`docs/engineering/release.md`) confirms the workflow is enabled and its last run was green.

**Amendment (2026-10-21, issue #12).** Two free protections for public repositories were off, and Actions could run any action at any ref. The maintainer set the following through the REST API on 2026-10-21; anyone with admin access can read them back:

- Secret scanning and push protection are enabled (`security_and_analysis.secret_scanning` and `secret_scanning_push_protection`). A push that contains a detected provider secret is blocked; bypassing it records a reason. Non-provider patterns and validity checks stay off.
- Actions may run only selected actions (`allowed_actions: selected`): actions owned by GitHub (`github_owned_allowed: true`) plus `sigstore/cosign-installer@*` and `goreleaser/goreleaser-action@*`, which `release.yml` uses. Actions from Marketplace verified creators are not allowed (`verified_allowed: false`).
- SHA pinning is required (`sha_pinning_required: true`): a `uses:` reference that is not a full commit SHA fails at job setup. This turns the existing practice of pinning by SHA into a rule GitHub enforces. The `check-actions-pinned` gate (issue #42) now catches an unpinned `uses:` in `make check` and on pre-push, before the push, rather than only at job setup.
- The default `GITHUB_TOKEN` permission stays read-only and cannot approve pull requests (unchanged).

Neither workflow needed a change. Every `uses:` was already a full commit SHA and every action is on the allowlist. A `workflow_dispatch` run of `nightly.yml` with `force_full=true` on `main` after the go1.26.10 toolchain bump (run 39665246214) succeeded in every job, including the full verify job, under the policy. `release.yml` runs only on tags, so it could not be dispatched. Reading it shows its four actions (`actions/checkout`, `actions/setup-go`, `sigstore/cosign-installer`, `goreleaser/goreleaser-action`) are all pinned by full SHA and matched by the allowlist. The first real tag is the live proof. The patterns allow any ref, so bumping a pinned SHA needs no settings change, while adding an action does.

To add a new third-party action, pin it by full commit SHA in the workflow and add an `owner/repo@*` pattern to `patterns_allowed` through `PUT repos/{owner}/{repo}/actions/permissions/selected-actions` (send the full list; the call replaces it). To read the current settings: `gh api repos/{owner}/{repo}/actions/permissions`, `gh api repos/{owner}/{repo}/actions/permissions/selected-actions` and `gh api repos/{owner}/{repo} --jq .security_and_analysis`.

**Amendment (2026-10-23, issue #41).** Dependabot alerts and private vulnerability reporting were off. The maintainer approved enabling both on 2026-10-22, and they were applied through the REST API on 2026-10-23:

- Dependabot alerts are enabled. Read back with `gh api -i repos/{owner}/{repo}/vulnerability-alerts` (HTTP 204 means on).
- Private vulnerability reporting is enabled. Read back with `gh api repos/{owner}/{repo}/private-vulnerability-reporting` (`{"enabled":true}`). Reporters use "Report a vulnerability" on the Security tab, and `SECURITY.md` points to it as the preferred channel.
- Automated security-update PRs stay off. Read back with `gh api repos/{owner}/{repo} --jq .security_and_analysis.dependabot_security_updates.status` (`disabled`). With no PR CI, nothing would gate the PRs Dependabot opens, so the maintainer triages alerts by hand. There is no release-checklist gate for alerts.

**Amendment (2026-10-26, issue #23).** The nightly full run now also runs `make fuzz` as its last step, after the goreleaser snapshot, so a fuzz finding never hides a later break. It fuzzes the hostlist line parser, the decoy line parser and `config.Load` for 60 s each, asserting no panic, typed errors and idempotent normalisation. On failure the next step prints the failing input from `testdata/fuzz/` into the log, because the runner is ephemeral. Like the rest of the nightly it is detection only: not a required check, no new action, and `permissions` are unchanged.

**Amendment (2026-10-26, rename).** The `nightly.yml` workflow is renamed `main-verify.yml` (workflow name `main verify`, concurrency group `main-verify-<ref>`, failure label `ci:main-verify-failure`). It verifies `main` after merge: it is dispatched with `force_full=true` after automated merges, and otherwise runs on the daily cron, which is a backstop (a vulnerability scan when `main` is unchanged). It is detection only and gates nothing. Behaviour, permissions and the cron expression are unchanged. "Nightly" and `nightly.yml` elsewhere in this ADR, and in the commit history, now mean the main-verify workflow.

**Amendment (2026-11-01, issue #27).** Nothing proposed dependency or tool updates, and the pre-commit hooks were pinned by mutable tag. Dependabot version updates are now on through `.github/dependabot.yml`, for three ecosystems: `gomod`, `github-actions` and `pre-commit`. Each runs weekly (Monday 06:00 UTC), is grouped into one PR per ecosystem, and has at most 2 PRs open. Titles use the `chore(deps)` prefix. The pre-commit revs in `.pre-commit-config.yaml` are frozen to commit SHAs, with the tag kept in a `# frozen:` comment, so the hook code cannot change under a re-tag. The `check-precommit-frozen` gate (issue #74) now refuses an unfrozen rev in `make check` and on pre-push. No version was bumped by this change.

- There is no PR CI, so the maintainer checks each Dependabot branch locally before merging. For `gomod`: `make ci` and `make pre-push`. If the `go` or `toolchain` line in `go.mod` changed, first set `mise.toml` to the Go version `go.mod` now selects. Pushing a commit to that branch stops Dependabot rebasing the PR. For `pre-commit`: `make ci` and `pre-commit run --all-files`, because main-verify never runs pre-commit. For `github-actions`: `make ci`. An action used only in `release.yml` is first exercised at the next tag.
- Dependabot's commits carry no DCO sign-off, so the maintainer squash-merges them (never rebase or merge-commit, which would land the unsigned commit on main) and edits the default squash message to add the `Signed-off-by:` line (`CONTRIBUTING.md`).
- main-verify is the post-merge backstop for `gomod` bumps and for action bumps in `main-verify.yml` only. Its `make ci` also checks that pre-commit revs are frozen (`check-precommit-frozen`, issue #74), though it still does not run the hooks.
- Dependabot's update jobs show in the Actions tab, but they are run by GitHub and are not workflows in this repository. "Nothing runs on pushes or pull requests" still holds for the repository's workflows, and the Actions allowlist needs no change.
- Security-update PRs stay off (issue #41 is unchanged).
- Dependabot does not watch the Makefile `*_VERSION` pins, `mise.toml`, the pnpm `packageManager` pin or `.nvmrc`. Those stay manual.

**Amendment (2026-11-05, issues #68 and #83).** `make fuzz`, main-verify's last step, now also fuzzes `hostlist.Load` (`FuzzHostlistLoad`) and `decoy.New` (`FuzzDecoyNew`), 60 s each like the others. They assert line accounting against a line-by-line oracle that splits the input itself, the per-source WARN cap, and that an empty source's error names a remediation. When the full run fails and no fuzz corpus file was written, the corpus step now says so and names the likely causes instead of printing nothing. This is detection only: permissions, actions and the cron schedule are unchanged.

**Amendment (2026-11-07, issue #54).** The full main-verify run now ends with a step, `upstream burst timing (evidence only)`, that runs `TestQuery_Burst100At20ms` verbosely under `-race`, 3 times at each of `-cpu 1`, `2` and `4`, so the burst time is in the log under a `GOMAXPROCS=` label (`make test` runs without `-v` and never prints it). `make fuzz` is therefore no longer the last step, as the 2026-10-26 and 2026-11-05 amendments call it. The step runs whenever the full run was not cancelled, even after an earlier step failed. It is `continue-on-error`, so it never gates: `make ci` still enforces the 500 ms burst bound, unchanged. It is a standing log, not a temporary one. It adds no action and leaves `permissions` unchanged.

### 2. Hook tiering with strict latency budgets

| Stage | Budget | Contents |
|---|---|---|
| pre-commit | ≤5s | trailing-ws, eof-fix, check-yaml/json, large-file, merge-conflict, mixed-line-ending, go-fmt, codespell |
| pre-push | ≤30s cold | one hook, `make -k -j8 pre-push`, running every gate concurrently: go mod tidy -diff, golangci-lint, go vet, full `go test -race` (`make test`), wasm compile and 5 MB size gate, go mod verify, **`govulncheck`**, check-public, check-spdx, check-testing-doc, check-licenses, check-actions-pinned, check-precommit-frozen |
| `make audit` (manual, pre-release) | unbounded | full `go test -race`, future syft+grype SBOM, future cosign verify of update-channel artifacts, pnpm audit signatures (when web exists) |

Note (2026-10-06): `make audit` today runs `go mod verify`, govulncheck and `goreleaser check`; the full race suite runs in `make ci`, and pnpm audit runs in `make audit` once a lockfile exists, not on pre-push.

Note (2026-10-20): the invariant gates run on pre-push through the same Make targets `make check`/`make ci` use, so the two cannot drift. Measured warm cost is about 2 s. They check the checked-out working tree (including untracked files), not the pushed commits; `make ci` on the commit you push remains the gate.

Note (2026-10-20, issue #25): the pre-push budget is measured cold, meaning empty Go build and golangci-lint caches (equivalent to `go clean -cache` plus `golangci-lint cache clean`), with the module cache and hook environments warm, on the maintainer's Apple M5 Pro. Measured 17.3/17.5/18.4 s cold, 8.8/9.0 s warm (was about 27 s cold). The hook runs the full race suite through `make test`, so the hook and `make ci` share one test timeout (`TEST_TIMEOUT`).

Note (2026-10-23, issue #42): `check-actions-pinned` is a pre-push hook through the same Make target `make check` uses (`make check-actions-pinned`: its self-test, then the scan of `.github/workflows` and `.github/actions` for a `uses:` that is not a full commit SHA). Measured warm cost is 0.46 to 0.47 s. Cold pre-push, same definition as the issue #25 note and taken on the same machine, three runs each: 18.4/17.5/18.5 s before the hook, 17.9/17.7/18.1 s with it. The difference is inside run-to-run variance, because the gate needs no Go build or lint cache, so it costs the same cold as warm; it stays under the 20 s budget.

Note (2026-10-23): the pre-push budget is raised from 20 s to 30 s cold, with the cold definition unchanged from the issue #25 note. Before, on the branch base, three runs: 24.6/22.0/22.5 s. After, three runs: 15.4/15.1/16.1 s. Run-to-run spread was 1.2 s (17.3 to 18.5 s, 2026-10-20) and 2.6 s (22.0 to 24.6 s, 2026-10-23). Between those dates, new tests pushed the same hook set past 20 s, so 20 s left no margin for noise or growth. Two changes brought the time down. The deadline tests in `internal/upstream` and `internal/dataplane` that own their state now run in parallel; the package time reported by `go test -race -count=1` (warm) went from 5.50 to 2.36 s for `internal/upstream` and from 4.39 to 4.09 s for `internal/dataplane` (the dataplane "before" figure came from a run of both packages together; the rest of `internal/dataplane` stays serial because `obs.Capture` swaps the global `slog` default, and so do the 4 port-bind tests). And every gate now runs concurrently as `make -k -j8 pre-push` in one hook; before, lint, vet, tests and the wasm gate ran concurrently in one `make -j4` hook, and the remaining gates ran as separate hooks one after another; `-j8` measured 15.4/15.3/16.6 s cold against 16.2/16.0/16.0 s for `-j4`. The current warm cost of `check-actions-pinned` is 1.53 s (median of three), which supersedes the 0.46 to 0.47 s in the issue #42 note: its self-test now runs the scanner 31 times over 11 throwaway repositories, and the gate runs alongside the heaviest step, not after it.

Note (2026-11-08, issue #61): `make vet-32bit` runs `go vet ./...` for `linux/arm` (GOARM=7) and then for `linux/386`, so a constant expression that overflows a 32-bit `int` fails the gate, test files included (a runtime `int(int64)` conversion still compiles and truncates silently, so vet does not catch it). It is a prerequisite of `make check`, so `make ci` and main-verify run it; it is not a pre-push hook. Measured cold on its own (a throwaway `GOCACHE`, the same cold definition as the issue #25 note) on an Apple M5 Pro with `/usr/bin/time -p`: `linux/arm` 3.33 s real, 35.05 s user+sys; `linux/386` 3.37 s real, 34.88 s user+sys. That is about 70 CPU-seconds in total that would compete with the race suite under `make -k -j8 pre-push`, and the gate has not yet been timed inside a full cold pre-push run, so it stays out of the hook until it has. A 32-bit break is still caught by `make ci` before a factory merge and by main-verify on `main`. Moving it into pre-push is a one-word Makefile change.

Note (2026-11-13, issue #117): `make lint` also lints `cmd/wardwasm` for js/wasm (`GOOS=js GOARCH=wasm golangci-lint run ./cmd/wardwasm/...`, after the host run), because golangci-lint loads packages with host build constraints and `cmd/wardwasm/main_js.go` (`//go:build js && wasm`) was never linted. `make check`, `make ci` and pre-push run it through `lint`. Same config, no linter or exclusion changed; it only adds code to lint. Measured on an Apple M5 Pro by wall clock, fresh `GOCACHE` and `GOLANGCI_LINT_CACHE` per run (the issue #25 cold definition), three runs each, alternating base and head (@ = 1-minute load average at the start of the run): cold `make lint` 7.7 s @3.73 / 5.7 s @1.93 / 6.1 s @1.94 (base) vs 10.5 s @3.60 / 8.4 s @1.81 / 8.1 s @1.65 (head), median +2.3 s; cold `make -k -j8 pre-push` 22.6 s @1.94 / 19.7 s @1.99 / 19.1 s @2.67 (base) vs 21.3 s @1.82 / 21.2 s @1.93 / 19.5 s @4.40 (head), median +1.5 s (base spread 3.5 s, so the spread arm of the budget rule does not apply; the delta is under +2 s). The js pass adds less to pre-push than to `make lint` because lint runs alongside the race suite. A fourth head run started at load 1.94 took 491.6 s while unrelated processes on the shared machine drove the load to about 48; it is not counted, and a fifth head run (re-run) started at load 1.88 took 19.2 s. Head stays under the 30 s budget.

Note (2026-11-22, issue #52): the pre-push gates keep checking the work tree, not the pushed commits. The risk that stays: a gate can pass on the work tree while a pushed commit fails it. That happens when a violation is committed and then fixed or deleted in the work tree without a new commit, when the pushed ref is not the checked-out branch, or when a commit inside the pushed range fails and a later one fixes it. It stays for three reasons. Every pre-push gate checks the work tree, not only the invariant gates: lint, vet, the race suite, the wasm gate and `go mod tidy -diff` build what is checked out, so moving only the invariant gates to the pushed commits would leave each push checked half against the commits and half against the work tree. Checking every gate against each pushed commit needs a separate checkout per commit and, by estimate (not measured), close to a cold build per commit, because each checkout recompiles the repository's own packages and re-runs lint even when the module and build caches are shared. One cold pre-push already takes 28.14 to 30.70 s (median 29.93 s over six runs, 2026-11-22, same definition as the issue #25 note), so by that estimate one extra cold build would exceed the 30 s budget. And pre-commit reads the pre-push ref lines itself and gives the hook one range (`PRE_COMMIT_FROM_REF`, `PRE_COMMIT_TO_REF`) for the first ref that needs checking, so a commit check would need hook wiring of its own. What bounds the risk: `make ci` run on a clean checkout of the commit you push (it too reads the work tree); main-verify, which runs `make ci`, with every invariant gate, on a clean checkout of `main` after merge; GitHub's `sha_pinning_required` (§1), which fails an unpinned `uses:` at job setup, so one that slips past cannot run; and secret scanning push protection, which checks the pushed commits on the server for provider secrets only, not for what check-public, SPDX, the testing doc or the licence gates check. A pre-push check that the work tree matches `HEAD` was considered and rejected: it blocks pushing with uncommitted work and still misses another pushed ref and a bad commit inside the range.

Note (2026-11-22, issue #52): threat model for the local supply-chain gates. `check-actions-pinned`, and any later local gate of the same kind (for example one for frozen pre-commit revs, issue #74), is an early, local warning for accidental mistakes, such as a tag typed where a SHA belongs or a pin lost in a copy and paste. It is not the enforcement. For Actions, the enforcement is the repository setting `sha_pinning_required: true` (§1 amendment of 2026-10-21), which GitHub applies at job setup whatever the YAML spelling, with actionlint (`make check-workflows`, run by `make check` and `make ci`) behind it. Anyone who can commit a deliberately obscured file can also edit or delete the gate script, so the gate does not try to stop them. A gap whose only trigger is a deliberately obscured spelling (for YAML: escapes, tags, anchors, explicit `?` keys, flow-style tricks) is an accepted residual. A review rates it a nit, not a blocker, and no rule is added for it; the gate's own note lists it if it is worth naming. A gap that an ordinary, accidental spelling can hit is still a defect in the gate.

Note (2026-11-22, issue #52): `check-actions-pinned` now fails closed on YAML forms its line scanner cannot read, even when the value is pinned. These are: any line, other than a block `uses:` line or a full-line comment, where `uses` as a whole word is followed by `:` (flow mappings such as `- {uses: …}`, quoted keys, nested sequences, and `uses:` in a `run:` script or a trailing comment); an explicit `?` key, in block style or inside a flow collection; an alias in a key position; a double-quoted key in a key position with a backslash escape, with or without a tag or anchor in front; text other than a `#` comment after an unquoted value on a block `uses:` line, or a flow indicator (`,]{}`) inside that value (a flow collection that goes on, or a second key on the same line, with or without whitespace before it); a backslash in a double-quoted `uses:` value, because the scanner does not decode escapes and would end the value at an escaped quote; and a line break other than LF (bare CR, U+0085, U+2028, U+2029). Each can name a `uses` key that the block `uses:` check does not read. The word boundary keeps other keys such as `statuses:` (a `permissions:` scope) and `max_uses:` legal; they are different keys, so this opens no bypass. Keys are case-sensitive, so `Uses:` is not a `uses` key. Merge keys (`<<: *step`) need no rule, because the anchored mapping is written out in the same file and its `uses:` is checked there. What stays refused, the cost of failing closed: `uses:` as a word in script text or in a trailing comment, anything but a `#` comment after an unquoted `uses:` value, a flow indicator (`,]{}`) in an unquoted `uses:` value (which also refuses a local action directory whose name contains one), and a backslash in a double-quoted `uses:` value; reword or split the line, or rename the directory. The explicit-key, alias and escaped-key rules also fire on a line inside a block scalar (`run:`, `script:`, a body) that starts with `? ` (for example a JS ternary continuation in `actions/github-script`), with `*word…:` (for example Markdown bold such as `**Status:**`), or with a double-quoted string that contains a backslash and is followed by `:`, because a line scanner cannot tell such a line from a key. This is a documented cost, not a bug: the gate does not loosen those rules, and the error message says to reword. Move the `?` to the end of the previous line, or do not start the line with `*`; the selftest pins both cases. No workflow has any of these today. Accepted residuals, under the threat-model note above: a multi-line implicit key in flow style, with `uses` alone on a line inside `{ … }` and the `:` on the next line, which YAML 1.2 does not allow and which actionlint (`make check-workflows`, in `make ci`) refuses as a parse error (a rule for lines starting with `:` would misfire on the shell idiom `: "${X:?msg}"`); and any other deliberately obscured spelling these rules miss. `sha_pinning_required` (§1) refuses an unpinned ref at job setup whatever the spelling. Warm `make check-actions-pinned`: 1.68 s (median of three; 1.60 s on the branch base). Cold pre-push, six runs each, interleaved base and change, same definition as the issue #25 note: base 28.14/29.89/29.47/29.97/30.41/30.70 s (median 29.93 s), change 30.14/30.29/30.26/30.17/30.18/30.82 s (median 30.22 s). The 1-minute load was 3.16 at the first run and climbed to about 27 during the set, largely from the back-to-back cold runs themselves, so the absolute figures are load-inflated and not comparable with the issue #117 note; only the base-to-change delta (0.29 s) is used. The change's median of 30.22 s is nominally over the 30 s cold budget, as is the base's 29.93 s within noise; whether the budget needs a new measurement or the re-evaluation ladder below is tracked in issue #126.

Note (2026-11-22, issue #74): `check-precommit-frozen` refuses an external hook repo in `.pre-commit-config.yaml` whose `rev:` is not a full 40-hex commit SHA followed by a `# frozen: v<tag>` comment. That is the form `pre-commit autoupdate --freeze` writes and the form Dependabot's pre-commit updater keeps (it replaces the SHA and the version in the existing `# frozen:` comment). `local` and `meta` repos need no rev. It is a pre-push hook through the same Make target `make check` uses (`make check-precommit-frozen`: its self-test, then the scan of the real config). Pre-commit revs have no server-side enforcement, unlike Actions' `sha_pinning_required` (§1): the checks are this local gate, then main-verify's `make ci` after merge. The gate is a bash line scanner, so `make check` needs neither Python nor pre-commit, and it follows the threat model in the 2026-11-22 issue #52 note: it catches an accidental mutable rev (a plain `pre-commit autoupdate` without `--freeze`, a careless edit, a Dependabot update). Accepted residuals: a deliberately obscured YAML spelling beyond the ones the scanner already refuses (it refuses a line break other than LF inside a line, flow or aliased `repos:`, a second `repos:` key, quoted, tagged or explicit keys, and a repo item that is not a block mapping). It fails closed only on the block-style forms it reads. The residuals it does not catch: a flow-collection closer (`]` or `}`) at the item indent or column 0, and a double-quoted scalar continued on a less-indented line, either of which can end the repos block early so that later lines are not scanned; an escaped quote inside a double-quoted rev; and a column-0 line starting with `|`, `>`, `%` or `@`. The maintainer ruled that no scanner rules are added for deliberately obscured spellings. Accepted false refusals, the cost of failing closed: a BOM before `repos:`, quoted or flow keys, openers such as `- # comment`, and a frozen tag without a leading `v` (what `--freeze` writes for such repos). Measured warm cost of `make check-precommit-frozen`: 1.29 s (median of three; 1.29/1.29/1.30 s), nearly all of it the self-test, which runs the scanner about 40 times over throwaway repositories. Cold pre-push, `make -k -j8 pre-push`, same cold definition as the issue #25 note (`go clean -cache` and `golangci-lint cache clean` before each run), three runs on the branch base and three with the gate, alternating base and change (@ = 1-minute load average at the start of the run): base 29.44 s @9.00 / 29.83 s @16.43 / 30.49 s @19.78, change 30.04 s @15.47 / 30.15 s @21.73 / 31.20 s @18.90. Medians 29.83 s and 30.15 s; the base-to-change difference is 0.32 s. The load climbed during the set, largely from the back-to-back cold runs themselves, so the absolute figures are load-inflated and only the delta is used. Whether the pre-push budget needs a new measurement or the re-evaluation ladder is tracked in issue #126; this note claims nothing about it.

Re-evaluation ladder if pre-push exceeds 30s sustainably:

1. Move the full race suite off pre-push to `make ci` only, keeping a fast subset on pre-push.
2. Once the repo is public, move the heaviest checks into a pre-merge GitHub workflow as required checks.
3. Last resort: move the slowest remaining pre-push checks to the nightly workflow (§1, `nightly.yml`), which already runs `make ci`, `make audit` and `make dod` against `main`. This trades detection before push for detection within a day of merge.

Note (2026-10-20, issue #11): step 3 previously read "nightly local launchd job runs `make audit` against HEAD". The nightly GitHub workflow replaces it: it runs on a clean machine rather than one checkout, verifies `main` rather than a local HEAD, and reports a failure as a repository issue rather than on one laptop.

### 3. `git push --no-verify` is a policy violation

The pre-push hook is the only enforcement point until public-repo CI exists. Bypassing it via `--no-verify` is a deliberate violation of this ADR; the committer is on the hook to manually run `make ci && make audit` before the next push, and to roll back the bypassed push if either fails.

### 4. Vulnerability scanning

**Go:** `govulncheck` (golang.org/x/vuln) — call-graph aware, fewer false positives than SBOM scanners. Pinned in `.tools/` via `GOVULNCHECK_VERSION` in the Makefile. `gosec` continues to run as a golangci-lint linter for static SAST. Dependabot alerts (§1 amendment of 2026-10-23) complement it: they flag any vulnerable dependency version in the Go modules listed in `go.mod`, whether or not the code reaches it. JS manifests are covered once `web/` or `site/` declare dependencies. Actions pinned by full commit SHA (§1, issue #12) get no Dependabot alerts, because GitHub only alerts for actions referenced by a semantic version. Version updates (§1 amendment of 2026-11-01) do bump SHA-pinned actions, though alerts still do not cover them. `govulncheck` stays the call-graph gate.

**JS/TS (once `web/` and `site/` package.json files exist):** `pnpm audit --audit-level=moderate` + **`pnpm audit signatures`** (verifies npm provenance attestations — the supply-chain defense most repos skip). Both run on pre-push via the `make audit` recipe.

**Deferred to sub-project 8 (release pipeline):** `syft`-generated SBOM, `grype` CVE scan, `cosign` signing, SLSA Level 3 attestation. Day-to-day, govulncheck + pnpm audit signatures are sufficient.

### 5. Package manager: pnpm only; runtime: Node 24 LTS

**Rejected alternatives:**

- **Bun (Oven Inc):** Fast, integrated, but a security-positioned product should not bet on a young runtime where threat-model surface and audit history are still maturing. Reconsider in 2027.
- **Deno:** Best security model (capability-based permissions), but the npm-compat layer adds friction for a stack built on shadcn / Astro / React (both Node-first). Worth considering for any standalone CLI utility we ship later.
- **Yarn Berry:** PnP is a strict-isolation win, but cybersec/devops momentum has shifted to pnpm.

**Enforcement:**

- `packageManager: pnpm@9.15.0` in root `package.json` — corepack rejects `npm install` for any contributor.
- `engines.node >= 24.0.0` + `.nvmrc` pinned to `24` (Node 24 LTS "Krypton", Active LTS since 2025-10-28).
- `.npmrc` sets `engine-strict=true`, `audit-level=moderate`, `node-linker=isolated`, registry pinned to `https://registry.npmjs.org/`.
- `onlyBuiltDependencies: []` — every package needing postinstall must be explicitly added to the allowlist. Directly mitigates the axios / TanStack attack class described in `docs/product/pitch.md`.

### 6. Future capability-based runtime sandboxing

When `web/` or `site/` ship real build pipelines, evaluate Node 24's `--permission` mode for build-time script isolation. Not required for v0.1; revisit when JS surfaces are non-trivial.

## Consequences

- Pre-push becomes mildly slower (about 9 s warm and 18 s cold as of 2026-10-20, ≤30s cold budget) — acceptable for the supply-chain guarantee. As of 2026-10-23, with all gates in one concurrent `make -k -j8 pre-push` hook, it is about 15 to 16 s cold (15.4/15.1/16.1 s) and about 5 to 7 s warm (5.4 to 7.2 s over 10 runs).
- The `check-actions-pinned` gate adds about 0.5 s to pre-push (a few lines of bash over the workflow files, no build cache involved) and means an unpinned `uses:` is caught before the push instead of only at job setup. That figure is from 2026-10-20 to 2026-10-23; the gate now measures 1.5 s warm because its self-test grew, and it runs concurrently with the heavy step instead of after it.
- The `check-precommit-frozen` gate adds about 1.3 s warm to pre-push (mostly its self-test, no build cache involved) and a cold pre-push difference of 0.32 s measured against its base (2026-11-22; see the issue #74 note in §2), and means an unfrozen pre-commit rev is caught before the push.
- Solo dev can choose to bypass with `--no-verify`; that is a documented policy violation, not an accident.
- No green-checkmark hygiene burden on GitHub; contributors run `make ci` locally.
- A nightly workflow re-verifies `main` after merge. It costs a few runner-minutes on days `main` changed and a minute or two otherwise (free for a public repository). A failure surfaces as one open `ci:nightly-failure` issue, not as a red check on a pull request, so a break can sit on `main` for up to a day.
- If the repository sees no activity for 60 days, GitHub disables the nightly schedule. It is re-enabled by hand (`gh workflow enable nightly.yml`); the release checklist catches it.
- Adding a third-party action now needs a repository setting change as well as a workflow change, and an unpinned `uses:` fails at job setup rather than in review. Both are deliberate.
- Dependabot alerts surface in the Security tab and open no PRs. Version updates open up to three grouped PRs a week, which the maintainer checks and merges by hand. Vulnerability reports arrive privately as draft security advisories rather than public issues.
- Re-introducing PR CI later means adding a `pull_request` trigger that runs `make ci` with the policies captured here as required checks; `nightly.yml` already runs the same targets on `main`.

## Revisit conditions

- Pre-push latency exceeds 30s for ≥2 consecutive weeks on a cold push (empty Go build and lint caches).
- A CVE arrives that `govulncheck` does not detect but `grype` or Socket.dev would have. Pulls SBOM tooling into pre-push.
- Bun, Deno, or another runtime gains a credible security track record (Sigstore-equivalent provenance, formal audits) that justifies a swap. ≥18 months sustained signal required.
- Outside pull requests arrive faster than local review can keep up with. (The repository going public on 2026-10-05 was considered and did not by itself trigger CI; see the §1 amendment.)
- The nightly workflow catches, within one month, two breaks on `main` that a pre-merge check would have caught. Pulls PR CI forward.
- PR CI exists. Reconsider automated Dependabot security-update PRs then, since checks could gate them.
- A Dependabot alert stays open and unread for more than a release cycle. Set a triage cadence or add a release-checklist check then.
- A Dependabot version-update PR stays open for more than a release cycle. Set a merge cadence, or reconsider that ecosystem's schedule or the feature.
- A pushed commit fails a pre-push gate that passed on the work tree at push time (found by main-verify or by hand). Then check the pushed commits (§2 note of 2026-11-22, issue #52).
