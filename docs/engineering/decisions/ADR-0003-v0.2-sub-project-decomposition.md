# ADR-0003 — v0.2 Sub-Project Decomposition

- **Status:** Accepted
- **Date:** 2026-05-25
- **Author:** Ujjaval Verma
- **Spec:** internal design notes (not published); this ADR is the durable summary
- **Amends:** the foundation design's sub-project table, row 10 (internal design notes, not published; crystallized into ADR-0001 D2) — adds internal structure to sub-project SP10 without superseding its scope.
- **Editorial note (2026-10-05, ADR-0007):** citations of unpublished notes reworded; the SP10b adapter label renamed "reference sibling adapter" per ADR-0006; sub-project count corrected to five.

## Context

The foundation design's sub-project table (internal design notes, not published; its durable decisions are crystallized in ADR-0001) enumerated sub-projects 1–9 (foundation through public flip) plus SP10 = v0.2 (Gemma slow-path + model abstraction + adversarial-eval suite, per ADR-0001 D2), SP11 = v0.3 (Roaming Mode, per ADR-0001 D3), SP12 = Phase 2 (native macOS, per ADR-0001 D3). The v0.2 entry was a single line; it was correct at the time but never internally decomposed.

`docs/engineering/definition-of-done.md` now carries four v0.2 acceptance bullets (12–15) that all cite "ADR-0001 D2" as their Source. That citation is technically correct but coarse: it gives slice intake no map of which bullet a slice flips, no dependency order, and no notation that distinguishes "this is the model-contracts slice" from "this is the adapter slice." Every v0.2 implementation slice would otherwise have to re-derive that graph at T0.

ADR-0003 lands the decomposition *before* the first v0.2 implementation slice opens, so T0s have something concrete to cite.

## Decision

SP10 decomposes into five lettered sub-projects: SP10a–d below, plus SP10e, added on 2026-05-26 (see below). Letter-suffix notation preserves ADR-0001 §8 numbering verbatim — SP11 stays = v0.3, SP12 stays = Phase 2 — and avoids a repo-wide grep-rewrite of prior `sub-project N` references.

### Dependency graph

```
SP10a ─┬─► SP10b ─┬─► SP10c ─► SP10e
       │          │
       └──────────┴─► SP10d
```

SP10a is the bottleneck — nothing in v0.2 can start without the Verdict type pinned. SP10c and SP10d are independent of each other and can ship in either order, or on parallel branches. SP10e is **deferred** and runs after SP10c (it consumes the verdict-carrying decision SP10c emits but currently does not apply).

### Why bullet 14 lives in SP10c, not SP10b

DOD bullet 14 asserts two things: (1) the adapter runs as a sibling process (invariant 3); (2) `ward serve` continues responding to DNS after the sibling is `SIGKILL`'d, emitting `policy: model unavailable` (invariant 7). Item (1) is established by SP10b's adapter design. Item (2) is *dataplane fallback behavior* — it lives in `internal/dataplane` + `internal/policy`, both touched by SP10c. The verification harness for bullet 14 exercises (2), so the bullet flips when SP10c ships. SP10b is a structural prerequisite (without sibling-process design there is no SIGKILL to survive) but does not on its own flip the bullet.

### SP10b has no DOD bullet of its own

SP10b is the only sub-project here without a dedicated bullet flip. Its acceptance is *implicitly gated* through SP10c's bullet 14 (which cannot pass unless SP10b's sibling-process adapter exists). This is a deliberate exception to the DOD doc's norm "the slice that lands the feature also turns its bullet green in the same commit." Slices opened against SP10b should call this exception out at T0.

### Why SP10e exists (added 2026-05-26)

SP10c shipped observe-only per the slice's lens-B DEFERRED operator pick D1 (recorded in the SP10c spec review; internal notes, not published): `DecideWithVerdict` is called on the slow path and the resulting verdict is logged at WARN/INFO/DEBUG by `dataplane.classifyAsync`, but `Decision.Action` is NOT applied to the connection. The observe-only narrowing was the right call for v0.2 — it ships the model→policy plumbing under DOD scrutiny without coupling the v0.2 ship date to a runtime-mutable enforcement matcher whose race semantics and observability surface were not yet specced.

SP10e is that enforcement work. Likely surface: a new `internal/policy/runtime` package holding a `sync.Map` keyed on qname; `policy.Engine.Decide` consults it before the static matchers (so a learned block beats a fast-path forward); `dataplane.classifyAsync` calls `Engine.LearnBlock(qname, verdict)` on success. 1–2 production Go files; well under the 3-file cap. SP10e does not flip a v0.2 DOD bullet — bullet 13 + 14 already PASS via the observe-only fork — so it ships as a v0.2.x maintenance slice or rolls into v0.3.

The SP10c spec promotion (slow-path observe-only narrowing, `policy: classified` log shape, verdict-to-log-level mapping) is folded into ADR-0004's "Annexes" section in the same chore that lands this SP10e row.

## Consequences

- `docs/engineering/definition-of-done.md` bullet 12–15 Source column is rewritten to cite SP10a–d (see DOD doc for the new strings). `scripts/dod.sh` bullet 12–15 stub `record TODO` descriptions are updated to match.
- The foundation design's sub-project table (row 10) is unchanged. ADR-0003 *amends with internal structure*; it does not supersede that table. ADR-0001 D2, which records that the slow-path model lands in v0.2, is likewise unchanged.
- Future ADRs for v0.3 (SP11a/b/...) and Phase 2 (SP12a/b/...) follow this same shape if those phases need internal decomposition.

## Alternatives considered

- **Renumber:** SP10/SP11/SP12/SP13 for v0.2 internals, push v0.3 → SP14, Phase 2 → SP15. *Rejected* — requires amending ADR-0001 §8 plus every prior `sub-project N` reference in the repo (release.md, invariants.md, ADR-0002, etc.). Number churn for no notational gain.
- **Decimal notation:** SP10.1/10.2/10.3/10.4. *Rejected* — visually indistinguishable from semver version numbers; invites confusion in commit messages and DOD output.

## Revisit conditions

This ADR is reopened if any of the following hold:

- SP10b's adapter design forces a contracts revision back in SP10a (would mean SP10a shipped prematurely).
- SP10d's eval work reveals the threshold-gate logic belongs in the dataplane runtime, not a separate `ward eval` subcommand (would re-fold SP10d into SP10c).
- SP10b's RPC contract proves the adapter is not actually a deep module (would collapse SP10b + SP10c).
- **SP10c's eventual T0 finds the bundled scope (bullets 13 + 14) exceeds the 3-production-file slice cap.** Re-split into SP10c (bullet 13) + SP10e (bullet 14). SP10c's T0 MUST enumerate the production files it touches before clearing the slice-budget gate — the bundled scope is on the edge of the cap and is unverifiable from this ADR alone.
